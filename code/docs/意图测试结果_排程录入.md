### F-01 地点提取过度依赖动词（最严重，30/63）

- **复现**：`总统府 中山陵 明孝陵` / `夫子庙、老门东、中华门` / `南京博物院 1.5 小时` / `夫子庙（夜景）` / `上午十点半到南京博物院`
- **期望**：`slots.must` 含对应地点（3 个 / 3 个 / 1 个 / 1 个 / 1 个），地点数正确
- **实际**：`kind=ask`，`must=[]`（数量词句 E-46/E-49/E-50 则只录到部分）
- **根因**：`Consultant.absorb()` 里 `must` 只有三个来源：`(?:想去|要去|…|去|逛逛|参观|游览)\s*(...)` 的并列切分、`(?:再加|加个|加上|…)\s*(...)`、以及"必须/一定要/必去"限定句。**没有任何一条规则做"整句地名扫描"**，所以只要句子里没有游玩动词，地名就一个都不进 `must`。
- **最小修复建议**：在 `absorb()` 末尾加一条兜底：先用 `_place_in_chunk` 已有的"去时长/动词噪声"逻辑切成候选段（`[和、,，跟与及＋＋\n→\-]` 与 `\s{1,}` 都当分隔），对每个长度 ≥2 的段跑 `_resolve_place`，命中且 `kind` 不是 `交通/住宿` 就进 `must`（沿用现有上限 5）。这条兜底与现有动词规则并列即可，不需要改动词正则。

### F-02 中文数字不在词法里（13）

- **复现**：`11月14号开始，三天两晚` → `days_total=1`（期望 3）；`想玩三天，你帮我排` + `11月14号开始` → 1（期望 3）；`从没去过南京，11月下旬四天` → 3（期望 4）；`去三个地方：A、B、C` → 只录 2 个
- **期望**：中文数字与阿拉伯数字等价
- **实际**：`plan.days_total` 由 `date_span` 兜底成 1 或窗口默认 3；数量词完全不生效
- **根因**：`(?:一共|总共|去|待|玩|住)\s*(\d{1,2})\s*天`、`(?:每天|一天|每日)\s*(?:最多|别超过|不超过|就)?\s*(\d)\s*个\s*(?:点|地方|景点)`、`(?:改成|改到|变成|调整成|调整为)\s*(\d{1,2})\s*天` 全都硬写 `\d`；`parse_party` / `parse_pace` 里的中文数字能力没有复用到这里。
- **最小修复建议**：抽一个 `cn_num(s) -> int|None`（一~十五、两、半 等），把上述三处正则的数字段改成 `([\d一二三四五六七八九十两]{1,3})` 再统一过 `cn_num`；`两天一夜`/`三天两晚` 另加一条 `([\d一二三四五六七八九十两])天([一二三四五六七八九十两])晚` 的规则直接产出 `trip_days=前天数`。

### F-03「1.5 小时」被日期解析器抢走（3，且会生成"过去日期"草案）

- **复现**：`南京博物院 1.5 小时`、`夫子庙逛1.5小时`、`总统府（1.5小时）`
- **期望**：`slots.start` 为空（用户在报地点和时长，没说日期）
- **实际**：`kind=plan`，`slots.start='2026-01-05'`，并附一句 `2026-01-05 已经过去了：我按你说的这个日期排`
- **根因**：`parse_date_range/parse_single_date` 把 `1.5` 里的 `1` `5` 当成了"1 月 5 号"，且日期规则在 `absorb()` 里早于时长识别执行。
- **影响**：比"识别不出"更糟——系统会拿一个凭空生成的过去日期出一整份草案，用户会以为是自己说错了。
- **最小修复建议**：在 `absorb()` 进日期解析之前，先把时长片段遮掉：`re.sub(r'\d+(?:\.\d+)?\s*(?:小时|分钟|h|H)', ' ', raw)` 再交给 `parse_date_range`。这条遮罩 `_place_in_chunk` 里已经有一份，直接抽成模块级函数复用。

### F-04 城市名/车站被当景点（1 已复现，风险面更大）

- **复现**：`头一回来南京，11月20号到22号，经典的都想去` → `slots.must=['南京站']`
- **期望**：`must` 不含城市名/车站（"去南京玩"不等于"去南京站"）
- **实际**：`回南京` 命中 `(?:我要)?回\s*(...)` 规则，`_resolve_place('南京')` 用前缀匹配落到 `南京站`（`kind='交通'`），而 `build_plan()` 的 `must_pois` 分支只过滤 `餐饮/商场/街区/商圈`，**不过滤 `交通`**，于是南京站会作为"景点"排进第一天
- **根因**：`_CITY_WORDS` 黑名单已存在（`absorb()` 里"去/逛 X"那条规则用到了），但"回 X"分支和 `_resolve_place` 都没有用它；`build_plan` 的 `must_pois` 也没有做同样的 `kind in ('交通','住宿')` 过滤。
- **最小修复建议**：① `_resolve_place()` 开头对 `_CITY_WORDS` 直接返回 `None`；② `build_plan()` 的 `must_pois` 循环补一句 `if str(poi.kind) in ('交通', '住宿'): continue`（与 `_pool()` 的口径对齐）。

### F-05 顺序结构「先A后B / A然后B」只吃一半（6）

- **复现**：`先去中山陵然后去明孝陵` → `must=['中山陵']`；`明孝陵完了去中山陵` → `['中山陵']`；`总统府出来接着去1912` → `['1912街区']`；`先总统府后夫子庙` → `[]`
- **期望**：两个地点都进 `must`（顺序本身另行讨论，见 PENDING-3）
- **实际**：只有"去 B"能被现有动词规则吃到，A 静默丢失
- **根因**：没有"连接词切分"这一步——`(?:去|逛|…)` 抓到的片段里不含 A，切分符表里也没有 `然后/接着/完了/之后/再/最后/先…后…`
- **最小修复建议**：按 F-01 的"整句地名扫描"兜底一并解决，不必单独加语法：把连接词并入分隔符集合即可。

### F-06 相对时间与节假日表述缺失（4）

- **复现**：`下周末去南京，两天就够` → `kind=ask`；`明年五一去南京玩四天` → `ask`；`国庆去南京，玩三天` → `ask`；`下下周一到周三，南京` → `start=2026-11-02, days_total=1`
- **期望**：分别解析成"下周末两天""2027 五一 4 天""国庆 3 天""下下周一到周三 3 天"
- **实际**：前三条只追问日期；第四条更糟——周次算错（"下下周一"给了 2026-11-02，即最近的周一），跨度也丢了
- **根因**：`proposal.parse_date_range` 的口径里没有 `周末 / 下周X / 下下周X / 节假日名`；`holidays.py` 已有节假日能力，但意图层没有接上。
- **最小修复建议**：日期解析层补 `本周/下周/下下周 + 周X`（含"周X到周Y"的区间）与 `周末`（周六~周日）；节假日名（国庆/五一/元旦/清明/端午/中秋/春节）走 `holidays.py` 查表。这条改动面最大，建议拆成两个小步。

### F-07 预算词汇表过窄（2）

- **复现**：`11月中旬去南京三天，预算不多` → `budget=''`；`11月21号到23号，两个人，预算一千以内` → `budget=''`
- **期望**：至少被记录（预算进 `budget`）；用户说法与默认值不同，就不能毫无反应
- **实际**：`budget=''`，`message` 里也没有任何提示
- **根因**：预算分支只有两组固定词 `省|穷游|预算少|学生`（→省）与 `不差钱|预算充足|随便花`（→宽），"不多""一千以内"都不在表里；金额上限也没有承载字段。
- **最小修复建议**：加 `预算不多/不太多/紧一点` 一支（→省）与 `(?:预算|花费|总预算)?\s*(\d{3,5})\s*(?:元|块)?\s*(?:以内|以下|左右)` 一支（金额先落 `note` 或新字段，怎么用见 PENDING-2）。

### F-08 节奏副词被静默忽略（2）

- **复现**：`11月25号到27号，节奏别太赶` / `12月22号到24号，带孩子，节奏慢一点` → `pace='normal'`、`per_day=3`
- **期望**：至少被记录（节奏进 `pace`，最好连带 `per_day` 降一档）
- **实际**：与默认完全一致，`message` 里无任何提示
- **根因**：节奏分支只认 `懒/起得晚/晚起/自然醒/不早起`（→slow）与 `特种兵/赶时间/多玩`（→fast）。"别太赶""慢一点""松一点"都不在表里；"别太累"只是因为 `太满/太多/累/少一点/少排` 那条减点规则里含 `累` 才碰巧生效（P-31 通过即证据）。
- **最小修复建议**：把 `别太赶/不赶/别催/慢一点/松一点/悠闲/别太累/不想太累` 并入 slow 一支；`赶时间/紧凑/多跑几个/一天多跑` 并入 fast 一支。

### F-09 「把 X 加到…」不在追加动词表（4）

- **复现**：`把中山陵加到明天上午` / `把老门东加到第二天下午` / `帮我把南京博物院加到行程里` / `把明孝陵加到11月14号下午`
- **期望**：`slots.must` 含对应地点
- **实际**：`must=[]`（其中两条因为句子里带日期还出了草案，草案里也没有这个地点）
- **根因**：追加规则是 `(?:再加|加个|加上|增加|添加|补个|补上|顺路去)\s*(...)`，"加到"不匹配；`exclusion_names` 也没兜到它，于是整句对 `must` 无贡献。而"把 X 加到明天上午"正是界面引导用户说的话。
- **最小修复建议**：把 `加到|加进|放进|排进|塞进` 补进那条追加正则；`加到` 后面通常直接跟时间状语（"明天上午"），需要复用 `_trim_to_place` 的"从尾部往前裁到能解析出地点"策略，避免把"明天上午"当地名。

### F-10 兴趣词表缺"夜景"（1）

- **复现**：`11月22号到24号，想看夜景` → `interests=[]`
- **期望**：夜间偏好被记录（进 `interests` 或独立时段偏好）
- **根因**：`_INTEREST_HINTS` 只有 历史/人文/博物馆/自然/美食/亲子 六类
- **最小修复建议**：`('夜景','夜游')`、`('夜市','美食街区')` 两条即可；`build_plan()` 里已经有 `EVENING` 点表（夫子庙/老门东/1912/秦淮/熙南里）与"排到当天最后"的逻辑，只缺一个把它接到用户话上的钩子。

### F-11 好景点被同名地铁站顶掉（附带，1）

- **复现**：`中山陵 明孝陵 灵谷寺` → `灵谷寺` 无法进 `must`
- **期望**：`灵谷寺` 解析到景区
- **实际**：`_resolve_place('灵谷寺')` 返回 `灵谷寺·钟灵街(地铁站)`（`kind='交通'`），随后被"交通类不进 must"的过滤掉，等于这个地点被静默丢弃
- **根因**：`_resolve_place()` 的候选排序按"规范化名字长度升序"取第一个，同名时地铁站比景区短，于是永远赢
- **最小修复建议**：候选排序加一条偏好：`kind` 优先取 `景点/公园/街区`（即 `_SIGHT_KINDS`），交通类排最后；或在同分时跳过 `(地铁站)`/`(公交站)` 后缀的条目。

## 5. PENDING-DECISION（需要产品决策，测试只做"必须与默认不同"的最弱断言）

1. **PENDING-1｜"节奏别太赶 / 节奏慢一点"落到哪一档**：只降 `per_day`（3→2）？只把 `pace` 置 `slow`？还是两者都改并连带起床时间？本组用例（P-22、P-32）只断言"与默认值不同"，具体档位未定，通过后需补精确断言。
2. **PENDING-2｜"预算一千以内"这类金额上限怎么用**：只筛住宿起价？还是同时约束门票+餐饮总额？现在只有 `省/宽` 两档，且金额无处存放。P-24 只断言"预算要有值"。
3. **PENDING-3｜"先A后B"的顺序是硬约束还是软偏好**：硬约束意味着要锁顺序、不许"顺路优化"重排；软偏好只作排序提示。E-29~E-36 只断言"两个地点都要进 `must`"，顺序未断言。
4. **PENDING-4｜"地点 + 时长"的时长记到哪**：目前没有"每点时长"槽位，`build_plan` 用的是 `intel` 推荐值。是要新增覆盖字段（用户说了就以用户为准），还是只当提示？E-11~E-20 只断言地点进 `must`。
5. **PENDING-5｜只有时长/只有地点、没给日期时，首轮该给草案还是先追问**：`consult.py` 模块文档写"先给一版再调：缺参数时给默认版 + 一句话说明"，实现选择先追问日期（并且第二次追问会退化成"按明天排"）。两种都自洽，但需要定口径。本组用两轮对话（P-42~P-50）绕开这个分歧，只测"补完日期后还记不记得用户说过的天数/地点"。
6. **PENDING-6｜"想看夜景"归哪一类**：兴趣（进 `interests`）还是时段偏好（夜间点置后）？两者都已有一半实现，选一个作为准绳。
7. **PENDING-7｜"把 X 加到明天上午"的语义**：是"往已有行程追加一条任务"（要落库）还是"改当前草案"？跨天尚未排程时应生成还是拒绝？E-37~E-40 只断言"X 进 `must`"。

## 6. 结论

**排程类 50 条通过 29、录入类 50 条通过 8；100 条里 63 条与契约不符（已 `xfail` 记录，未改任何产品代码）。这批用例最薄弱的三个点：**

1. **地点录入几乎全靠动词驱动**——只要句子里没有"去/逛/参观"，地点一个都进不了 `slots.must`。裸地名堆、地名+时长、地名（附注）、顺序句，30 条全落空；这是"录入类"崩掉的主因，也是"排程类"地点丢失的主因。
2. **中文数字没进词法**——天数与数量词正则硬写 `\d`，"玩两天 / 三天两晚 / 两天一夜 / 陪我玩四天 / 去三个地方" 13 条系统性失效，而"玩4天"能过，说明缺的只是数字分词，不是设计。
3. **相对时间和软约束被静默吞掉**——"下周末 / 明年五一 / 国庆 / 下下周一到周三"只回一句追问（其中一条还把周次和跨度算错），"预算不多 / 一千以内 / 别太赶 / 慢一点 / 想夜景"则毫无反应也不提示；用户无法察觉自己说的话没生效。

另有三处独立缺陷值得单列（都能稳定复现）：**① `1.5 小时` 被日期解析器读成 1 月 5 号，凭空生成一份"过去日期"草案；② "回南京"把城市名解析成 `南京站` 并当成景点排进行程；③ "灵谷寺"解析到同名地铁站后被交通类过滤，实际好景点被丢掉。**
