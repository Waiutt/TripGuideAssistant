## 0. 判定口径（来自任务契约，不是照现状写死）

| 组 | 契约 | 本文件的判定 |
| --- | --- | --- |
| 问答类 | 不得再生成一版新行程；应给出回答或明确的"做不到"提示 | `plan.days` 不存在，且 `kind ∈ {ask, notice}` |
| 指代不清 | 必须追问或明确说明，不许臆造成具体地点 | `kind ∈ {ask, notice}`，且新方案里不出现基准之外的地点 |
| 纯应答 | 给出可继续的下一步，而不是硬排 | `kind ∈ {ask, notice}` 或有待答问题（`questions` 非空） |
| 情绪与否定 | 接住这句话（问哪儿不满意 / 换出真正不同的一版） | `kind ∈ {ask, notice}`；"换一个"另判位点是否真的变了 |
| 条件句 | 必须追问或明确说明，不许当无条件指令执行 | `kind ∈ {ask, notice}`，且 `per_day` 不被条件句改写 |
| 超短输入 | 要么追问，要么真把天数/日期落进槽位（不许静默丢弃） | `kind ∈ {ask, notice}` 或 `trip_days/start/end` 发生变化 |
| 空输入与纯标点 | 不该被当成"再排一版" | `kind ∈ {ask, notice}` 且无 `plan.days` |

三种上下文：**已有一版行程**（先给 `11月14号到16号去南京玩，想去南京博物院、总统府和夫子庙，每天两个点`）、**full**（同上再加"住金陵饭店，午饭就近随便"，此时会话里已无待答问题）、**空会话**（一开口就含糊/就问）。

## 4. 疑似缺陷（复现 / 期望 / 实际 / 最小修复建议）

> 本节只记录，不改代码（`code/nanjingtrip/**` 本轮不动）。

### D-1（R1）一句话问句会被回成一版新草案，且"新"里没有任何回答

- 复现：先发 `11月14号到16号去南京玩，想去南京博物院、总统府和夫子庙，每天两个点`，再发 `为什么这么排`
- 期望：给出一句解释（为什么是这三个点、为什么这样串），或明确"这条我说不清"
- 实际：`kind=plan`，出了 5 个位点的新方案（与上一版相同），`message` 只有"3 天草案已就绪（每天 3 个点）"
- 最小修复建议：在 `Consultant.chat()` 里 `build_plan()` 之前加一个**只读**的分支：句子命中"吗/呢/多少/几/为什么/多久/远不远/推荐/开门/门票"等问句特征，且不带明确的修改动作（加点、删点、改天数、改日期、改节奏）时，返回 `kind='ask'`（或新增 `kind='answer'`），把已有方案的关键数据整理成一句答话；`plan` 字段一律不填。

### D-2（R2）问句里的日期会被当成"要去的那天"

- 复现：空会话里发 `明天会下雨吗`（或 `11月15号天气怎么样`、`周一闭馆吗`）
- 期望：回答天气/闭馆信息，或说明"天气只有当天 +3 天有预报"这类边界
- 实际：`kind=plan`，会话日期被写成 2026-11-02（或 11-15），排出 1 天方案（牛首山 + 午饭）
- 最小修复建议：日期抽取要带**句法条件**——句子是疑问句时，抽到的日期只作为"问句里的日期"传给回答层，不写进 `start/end`；改写槽位只允许发生在陈述句/祈使句（"改成11月15号""就明天吧"）。

### D-3（R3）问句里的数量词会改写节奏

- 复现：`第二天两点会不会太累`（已有一版行程，每天 3 个点）
- 期望：回答"两个点一天合不合适"，槽位不动
- 实际：`per_day` 3→2，方案掉到 2 个点/天，少了南京欢乐谷和牛首山
- 最小修复建议：`per_day` 这类**写槽位**的抽取，只在祈使/陈述句（"每天别超过两个点""每天两个点"）里生效；问句中出现数量词时只作为回答素材。

### D-4（K3/K4）带条件的句子会被"执行一半"

- 复现：`如果太累就少一个`（full 会话）
- 期望：追问"以什么为界？太累到什么程度算太累？保守一点还是先按 3 个点排？"，或明确说明"本系统不支持条件指令"
- 实际：条件被直接执行（`per_day` 3→2，午饭餐厅也跟着换人），而 `下雨就去博物院`、`要是太晚就直接回酒店`、`天气好就多走两个点` 则被静默丢弃——同一类句子的处理方式不一致
- 最小修复建议：句子里同时出现"如果/要是/…就…/万一"时，把整句标记为条件意图：不写槽位、不出方案，返回 `kind='ask'` 追问触发条件；条件意图与"改行程"意图的优先级要高于普通槽位抽取。

### D-5（K2）纯应答在"参数已齐"的会话里只是重排一遍

- 复现：full 会话（日期+必去点+住宿+吃饭都给全）里发 `好的`
- 期望：确认（"就按这版走"）+ 下一步提示（导出/看路线/改某天），或追问"要我改哪儿？"
- 实际：`kind=plan`、`questions=[]`、`message` 仍是"3 天草案已就绪（每天 3 个点）"，等于把排程又跑了一遍，用户看不出"好的"被听懂没有
- 最小修复建议：识别纯应答词表（好/行/可以/嗯/没问题/都行/随便/你定/听你的）→ 若当前会话已有方案，返回"沿用当前方案"的确认 + 一条可执行下一步；`build_plan()` 不必重跑（这也能省掉一次取数）。

### D-6（K5）超短输入被静默丢弃

- 复现：已有一版 3 天行程时发 `就一天` / `两天吧`
- 期望：改天数（`trip_days=1/2` 并重排），或追问"从哪天开始算一天？"
- 实际：`trip_days` 不变、位点不变、`kind=plan`，回复仍是"3 天草案已就绪"——用户以为说了，系统其实没听见
- 最小修复建议：给"仅数量+时间单位"的短句（`就?[一二两三四五六七八九十\d]+天`、`半天`、`一天半`）单独一条解析规则，写入 `trip_days`；解析不到起始日期时按现有 `start` 顺延并明说。

### D-7（K1）指代不清：这一组"臆造地点"守住了，但少了一句反问

- 复现：已有一版行程时发 `就去那边吧` / `老地方` / `那个景点加进去`
- 期望：追问"那边指哪儿？候选：夫子庙 / 老门东 / 1912 街区"
- 实际：`kind=plan`，位点与上一版**完全一致**（没有臆造地点，这一点是达标的），但用户不会知道系统没听懂
- 最小修复建议：只要句子里出现"那边/那里/那个/那家/老地方/前面说的/你懂的"并且没有可解析的地名，就走追问分支，把当前方案里的候选地点列 3 个给用户点。

## 5. PENDING-DECISION（需要产品决策，代码无从判断）

1. **"随便"到底给方案还是追问？** 本文件把 `随便吧`（full 会话，V-15）按"应给下一步"判为不通过；但另一种设计是把"随便"当作"你替我定"，直接沿用当前方案并说明"那我按现在这版定了"。同一个词在"缺日期"和"方案已齐"两种处境下可以有两套正确行为，需要产品定口径。
2. **"嗯/好的"是不是确认？** 若定义为"确认当前方案"，那 D-5 的正确行为是**不重排**而非追问（用例判定随之改）；若定义为"我在听，继续"，则应追问。当前实现两边都不占，属于未定义。
3. **"换一个"换什么？** 本文件要求"位点真的变了"。若产品认为"换一个"应优先追问换哪一类（景点/餐厅/住宿），用例判定应改为"必须追问"。当前实现两者都不是（位点不变）。
4. **"明天"（V-39）算不算问句？** 当前它把日期改成了明天并从 3 天掉到 1 天，无确认。若产品接受"单词日期→当日方案"的激进行为，这条可转为通过；若要保守，应追问天数。
5. **条件句是否入库？** "下雨就去博物院"若要真正支持，需要在会话里存"条件-动作"对（现在 `ConsultSession.FIELDS` 没有这个槽位），这是数据结构层面的决策，不是解析层能自行决定的。

## 6. 一句话结论

这两组最薄弱的三点是：**① 没有问答层**（`chat()` 只要日期齐就 `build_plan()`，30+3+1 条问句全部被回成一版新草案，还带日期/数量词这类写副作用）；**② 没有澄清层**（指代不清 10 条、纯应答 5 条、条件句 4 条、超短指令 2 条，共 21 条既不追问也不落实，条件句甚至"执行一半"）；**③ 缺少"不回答也要明说做不到"的兜底**（42 条通过里有 41 条只是被"你要哪天去？"这句追问挡了一下，用户问的天气、距离、门票一句没答）。

意图层建议按"**先判定、后执行**"切成三支，判定放在 `Consultant.chat()` 的最前面（在 `absorb()` 写槽位之前）：

- **ask**（只读）：句子是疑问句且不含修改动作 → 只读已有方案槽位与城市包/情报，组织一句答话或"做不到 + 原因"，返回 `kind='ask'`；**绝不写槽位、绝不 `build_plan()`**。问句里的日期、数量词只作为回答参数，不落到 `start/per_day`。
- **clarify**（不执行）：指代不清、条件句、纯应答、超短/空输入 → 追问一句 + 给候选（地点/天数/条件），返回 `kind='ask'` + `questions`；条件句需要新的槽位来表达，未落地前一律追问而不是执行。
- **plan**（写槽位 + 出方案）：只有明确的祈使/陈述修改（加点、删点、改天数、改日期、改节奏、报住宿吃饭）才进 `absorb()` → `build_plan()`。

三支的优先级 `ask > clarify > plan`（问句里带指令时按 ask 处理并确认），并且**每支都要有"不确定就说做不到"的出口**，避免用重排一版方案冒充回答。
