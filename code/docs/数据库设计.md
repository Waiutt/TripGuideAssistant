> 面向"接手/答辩/排障"的一份工程文档，与设计报告第 2.4 节（E-R 图、范化分析、表结构表 2.6–2.11）互补：

> 代码位置：`nanjingtrip/storage.py`（仓储与 DDL）、`nanjingtrip/services.py`（业务写入口）

## 一、为什么是 SQLite（与"完整 SQL"的关系）

| 维度 | 现状 | 说明 |
|---|---|---|
| SQL 能力 | 完整关系库：事务、外键（级联删除）、索引、`ALTER TABLE` 迁移、WAL | 不是"用文件代替数据库" |
| 部署 | 单文件、零安装 | 需求约束是"本地部署、数据只在本机/局域网、不搭服务端"，换 MySQL/Postgres 会凭空多一个必须运行的服务 |
| 规模 | 当前 128 KB；trip 9 / task 39 / poi 107 / transit_leg 311 / trip_version 88 | 单用户单机，服务端库的性能优势体现不出来 |
| 迁移 | 复制目录即迁移 | 换电脑演示只需拷 `NanjingTrip` 目录 |
| 并发 | 写入由 `db.lock`（RLock）串行化；两个实例同开一个库时 15 s 忙等待（缺陷 D-24） | 单进程单写者模型 |

**什么时候该换**：多台机器同时写同一份数据、需要远程多用户并发与权限隔离 → PostgreSQL；表数量继续膨胀、频繁改 schema → 引入迁移工具（Alembic）。换库时只需实现一个新的 `TripRepository` 适配器，领域层与应用层不改（端口/适配器的收益）。

## 二、表与索引

| 表 | 用途 | 关键约束 |
|---|---|---|
| `trip` | 一日一条行程（一城一日一份） | `plan_date` + `city` 联合唯一（迁移后） |
| `task` | 行程内事项 | 外键 `trip_id`（级联删除）、`poi_id` |
| `poi` | 地点（含城市包坐标与在线检索结果） | `(provider, provider_poi_id)` 唯一 |
| `transit_leg` | 通行时长缓存（起终点 + 方式） | `(from_poi_id, to_poi_id, mode)` 唯一 |
| `trip_version` | 每次排程后的快照（可回滚） | 外键 `trip_id` |
| `app_setting` | 键值配置（不含密钥） | 主键 `key` |

索引与理由：

| 索引 | 服务的查询 |
|---|---|
| `idx_trip_date_city` | 按日期 + 城市取当日行程（`get_day`，最热路径） |
| `idx_task_trip` | 取某行程的全部事项（`SELECT * FROM task WHERE trip_id=?`） |
| `idx_task_poi` | 按地点反查事项（删地点/改坐标后重排） |
| `idx_poi_provider` | `ensure_poi` 按 `provider + provider_poi_id` 查重 |
| `idx_version_trip` | 取版本列表（`trip_id, created_at` 倒序） |

## 三、关键 SQL 与写入路径

- **一日唯一**：`get_day(plan_date, city)` → `SELECT * FROM trip WHERE plan_date=? AND city=?`；`save_day/upsert` 按 `task_id` **增量**更新/插入/删除（早期"先删后插"导致 `task_id` 每次全变，是缺陷 D-11 的根因）。
- **地点坐标可纠正**：`update_poi_coord(poi, lng, lat)` 更新 `poi` 行；地图页"钉住坐标"走这里，随后 `replan` 重算各段通行。
- **通行缓存**：`transit_leg` 按 `(from, to, mode)` 唯一键缓存时长；在线来源与离线估算分别标注 `source`，切换在线后不采信离线缓存（缺陷 D-12）。
- **版本与回滚**：每次排程写一条 `trip_version`（含 `snapshot_json` 与 note），保留 `keep_versions` 条；回滚即按快照重建。
- **整天删除**：`delete_day(plan_date, city)` → `DELETE FROM trip ...`，靠 `ON DELETE CASCADE` 连带清 `task` 与 `transit_leg`。

## 四、迁移历史（`Database._migrate()`）

| 变更 | 做法 |
|---|---|
| `task.mode`（逐段方式） | `PRAGMA table_info(task)` 探测 → `ALTER TABLE task ADD COLUMN mode TEXT` |
| `poi.city`（多城市作用域） | 同法加列，默认空串 |
| `trip.city` + `trip.lodging_poi_id` + `lodging_declined` | 同法加列；`city` 默认 `'南京'`（老库视为南京） |
| `trip` 唯一键从 `plan_date` 改为 `(plan_date, city)` | **表重建**：建 `trip_new` → 搬数据（老库 city 填 `'南京'`）→ 删旧表 → 改名 → 重建索引 |

原则：**只增不删**、旧库能直接升级、升级过程可重复执行（`IF NOT EXISTS` / 列存在性探测）。

## 五、备份、恢复与排障

- **备份**：停服务后复制 `%LOCALAPPDATA%\NanjingTrip\`（含 `nanjingrip.db` 与会话产生的 `-wal`/`-shm`）；或用 `sqlite3 nanjingtrip.db ".backup backup.db"` 热备。
- **恢复**：把备份文件改名回 `nanjingtrip.db` 即可；版本表可单独用于"回到某次排程"。
- **常见故障**
  - `database is locked`：多半是上一实例未退出。已把忙等待抬到 15 s（D-24）；仍报错就确认是否开了两个进程。
  - 坐标错/点位可疑：地图页「① 确认点」会标红并给候选，一键 `pin_point` 纠正。
  - 数据看着"丢"了：先看是不是切了城市（一城一日一份）——用「更多 → 全部规划记录」核对。
