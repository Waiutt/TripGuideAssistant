## 三、预期能抓到什么（按今天实测的命中率）

今天新增的 39 条边界/可靠性用例共暴露 **6 个真缺陷 + 1 次自伤事故**（命中率 ~15–18%）。
按此推算：

- A+B 层：预计抓 **4–7 个**，其中 **2–3 个是"会丢数据/会崩"** 级别；
- C 层：预计抓 1–2 个（地名臆造或错分店）；
- D/E 层：命中率会降到 5% 以下，多数产出是"记录不修"。

## 四、弊端（必须知道）

1. **修复风险大于测试收益。** 今天已有一次自伤（改 `services.py` 丢了 `@property`，87 例同时红）。
   越接近交付，改动越危险。规则：只修"会崩 / 会丢数据 / 会误导用户"的，体验类只入缺陷表。
2. **测试会固化错误决定。** 例如 1200 字上限、窗口默认 3 天，一旦写成断言，后面想改就要改测试。
3. **套件变慢。** 现在 436 例约 60 s；再加 37 例约 +10–15 s；打包自检也要跑全量（现在 ~1 min）。
4. **假信心。** 边界测试只覆盖"我想到的边界"。今天的证据是：4 个真缺陷里 **3 个来自你实操**，不是我的用例。
5. **挤占交付材料。** 还缺演示视频、封面信息、评分表——这些是"不交就扣分"的硬项。
6. **前端脚本易碎。** 没框架、纯 DOM，Playwright 脚本靠选择器与时序，维护成本高；关键路径人工走一遍更划算。

## 五、不做（并说明理由）

| 不做 | 理由 |
|---|---|
| LLM 在线路径的边界扫描 | 结果不确定，只能断言结构/区间；已有 9 条联网验收 |
| 性能基准（并发压测/NFR 全量） | 已有一次性实测数据，做自动化基准收益低 |
| 跨城行程、多语言、导出 | 功能本身未实现（属"后续规划"） |
| 真机多端并发 | 需要第二台设备，人工验证过；成本高收益低 |

## 六、执行顺序（若批准）

1. A 层第一批：重复提交 + 并发两次写入 + 整日清空 + 回滚顺序
2. A 层第二批：20 项超长日 + 23:59 边界 + 无任务日
3. B 层：跨月/跨年/闰日/过去日期/脏格式
4. C 层前 5 条：不存在地名/地址串/同名异店/跨城/后缀
5. 每批跑完：`tools/audit_code.py` → 两套测试 → 同步报告口径
